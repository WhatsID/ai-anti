# 机制规则的由来事故档案

> **整理来源**：本文件的全部条目摘自来源业务仓库 `CLAUDE.md`「多模型接力工作流」
> 各节与 `AGENTS.md` 核心约束中的**日期注脚**，以及随迁的命令模板
> （`codex-review.md`、`codex-implement.md`、`qwen-review.md`、`opus-review.md`）
> 内的实测记录。整理时间 2026-08-13，随机制正文一并从来源业务仓库抽取到本仓库。
> 本文件只做**归集与索引**，不新增判断。2026-09-18 起，共用评审规则原文以
> `core/REVIEW_PRINCIPLES.md` 为准；`CLAUDE.global.md` 只保留 Claude Code 适配和实施编排，
> `core/CLI_DISCIPLINE.md` 仍是外部 CLI 调用纪律的唯一权威。旧日期注脚与事故事实不改。
>
> 用途：机制文件属于高风险触发器，改动前先读本文件——每条规则背后都有一次实际
> 付出的代价，看不出代价就容易把它当成风格偏好删掉。

## 2026-09-17 ｜ 模块尺寸与安全/资源进接力流程

**规则**：接力第 1 步的改动文件清单每个文件标「当前行数 → 改后预计」，触碰项目尺寸基线的
条目必须写明抽取步骤或写明为什么抽不动；第 5 步终审**复核尺寸门禁输出与抬线理由**；三档
评审通道都必须让评审方显式作答**评审四问**（安全两问、资源两问），四问正文以
`adapters/claude-code/CLAUDE.global.md`「评审四问」一节为唯一权威，模板只引用不复制。

**尺寸棘轮的由来（实际失败）**：来源业务仓库的一个前端组件出生就是 **2478 行**
（AI 一次写出），90 天 26 次提交后 **2866 行**；另一个组件从 708 行长到
**2377 行**。门禁落回当天即抓到同日另一个会话的提交把第三个组件一次加长
**205 行**（2081 → 2286）——规则立起来的第一天就拦到了它要拦的东西。

**安全四问的由来（实际失败）**：2026-08-29（来源业务仓库登记台账「升级 Next.js」
条），主模型此前判断 Next 的多条 CVE「双重不适用/高估」，**一次外部复审推翻了这个判断**
——它把新公告与旧 CVE-2025-29927 搞混，并误称本站没有 middleware，而该站其实有
middleware 文件。同一批复审还查出一个会话管理问题。**这两条都不是接力流程
的常规产物，是一次性的外部复审顺手带出来的**——四问要做的正是把这种偶然变成每轮固定动作。

**如实标注的部分**：「三个评审模板对『安全/性能/注入/内存』四词零命中」（2026-09-17 实测）
只是文本统计，它说明**没有人被要求去找**，不构成一次漏审事故；本条规则的另一半依据是
**用户 2026-09-17 明确提出的预防性要求**（request 第 1 轮：「后面两个点我目前没有机制来
确认这两点被关注到」）。两种依据分开写，不混为一谈，也不拿词频冒充事故。

**取舍**：①阈值不写死进正文，走「项目级覆写」表的 `模块尺寸门禁命令` 一行，项目没有就留空；
②四问放正文作唯一权威而非各模板抄一份，照 `core/CLI_DISCIPLINE.md` 的反漂移结构
（2026-08-11 模板间漂移事故：首次挂死 45 分钟、二次 2 小时 44 分）；③不给
`adapters/claude-code/agents/adversarial-reviewer.md` 加固定问题，改由 `opus-review.md` 的
派发把四问分配给视角，以免与它的空上下文设计冲突；④四问受「说不出失败场景不要写」约束，
防止它变成凑数条目的许可证。

**Codex 评审逐条裁决**（2026-09-17，Codex 通道，一轮 6 条）：2 条必修采纳（降级通道
qwen / opus 也必须接上四问——它们各自存着完整提示词副本，不会自动加载 Codex 的；来源业务仓库
覆写表补「模块尺寸门禁命令」一行，否则新会话取到「无」、第 5 步跳过门禁复核）；3 条采纳
（终审读方案或实施报告里的抬线理由，而非终审时点尚不存在的提交信息；由来按实际失败写实；
四问集中一处由三通道传入）；1 条登记（没有尺寸门禁的项目只记行数不等于落实拆分，已进
`docs/FEATURE_TODOS.md`）。

## 2026-08-18 ｜ qwen 档的模型传递方式与「三态判读」

**规则**：`/qwen-review` 的模型名必须走「档位别名 `--model sonnet` + 三个
`ANTHROPIC_DEFAULT_*_MODEL`」，不得用 `ANTHROPIC_MODEL` 直传；判这一发成没成**只看
输出文件能否解析出 JSON 及其 `is_error`**，`[claude-code:unrecognized_model]` 那一行
成功失败都出现、不构成判据。规则原文见
`plugins/qwen/commands/qwen-review.md` 的「要点」区。

**代价**：2026-08-18 在来源业务仓库的一次高风险任务（一处鉴权接口的 CORS 前缀匹配
修复）上真实付出。Codex 无额度、按阶梯降到②档，而模板记载的 `ANTHROPIC_MODEL` 直传
形态在 claude CLI 2.1.234 上被**客户端侧**的模型注册表拦下，请求根本发不出去，输出只
剩两行噪音。这种失败形态**与「本档不可用」无法区分**——差一点就按阶梯直接降到③档
Opus 同族评审，而③档明确要求「只在①②都不可用时启用」，等于**在通道其实健康的情况下
静默跳过跨模型评审，汇报里还会写着「已按阶梯降档」看起来完全合规**。

**排查花费**：五步定位（模板写法 → 加 `--model` → 改档位默认变量 → HTTP 直连证明
端点与模型都健康 → 找到可用组合）。若不把结论写进模板，下一个会话要把这五步重走一遍。

**2026-08-19 三态实测补记**（修正了初版的一处错误表述）：端点侧失败**是有 JSON 的**
（`is_error:true`、报文在 `result`，如 `Model not exist`），只有客户端侧拦下才没有
JSON；初版写的「无 JSON 时看 code 区分两侧」不成立。

**归属裁决**：该知识长远属于 `core/CLI_DISCIPLINE.md`（它约束一切 `claude -p` 同形态
通道），但当前这类通道只有 qwen 一个，上收不解决现实问题——**第二个同形态通道出现时
再上收**。

## 2026-08-12 ｜ 评审意见分诊规则

**规则**：评审意见分「必修 / 登记 / 驳回」三类处置，必修只认三条硬判据（数据丢失或
不可逆损坏、本次需求核心功能不工作、登录墙外的人拿到数据或进得来）；采纳必修项后
**不自动复审**，只有架构被整个推翻或出现 blocker 级新事实才开第二轮；评审最多共两轮。

**由来（用户指令立此规则时记录的事实）**：此前约 50 条意见零驳回、每次修订必复审，
导致轮次爆炸——**单日 15 轮评审只换来 3 个提交，其中 6 轮花在评审机制自身、2 轮产出
为零**。

**要点**：这条规则的成本不在「漏掉一条边界意见」，而在「每条意见都当必修」会把流程
本身变成产出。「采纳了很多条意见」明确不构成再评审理由。

## 2026-08-11 ｜ 外部 CLI 调用纪律（四条）

**规则**：见 `core/CLI_DISCIPLINE.md`（唯一权威）——命令末尾 `< /dev/null`、输出直写
文件禁接截断管道、提示词经文件传入、后台运行必须监控。

**由来**：

- **挂死**：非交互 CLI 会先等 stdin EOF，后台运行且 stdin 未关闭时**永远不开跑**，
  只打印一行 `Reading additional input from stdin...` 后无限空转。首次挂死 **45 分钟**，
  二次 **2 小时 44 分**。
- **静默丢条目**：输出接 `tail`/`head` 截断会吃掉开头的条目——2026-08-11 两次因此丢失
  评审清单的**前 2 条，其中含 blocker**，要靠额外一轮调用才补回来。
- **参数拆断**：长提示词内联进命令行时，提示词里的引号与 shell 引号打架，实测报错形如
  `error: unexpected argument 'xxx' found`。

**要点（这条纪律为什么必须是唯一权威）**：这些教训原先只记在
`codex-implement.md` 一个模板里、没记进兄弟模板 `codex-review.md`，于是同一个坑在
2026-08-11 **二次发作**。把知识收进单一权威条款、模板只引用不复制，正是为了终结这种
模板间漂移。

## 2026-08-07 ｜ 评审通道降级阶梯与「会话内不重试」

**规则**：评审通道按 ①Codex → ②qwen 插件 → ③Opus 5 子代理同族评审 → ④停下问用户
逐档下降；③档必须执行空上下文、立场固定、3–5 个不同视角、自跑探针、blocker 独立复核
五项补偿条款，缺一即不算过评审；①或②任一恢复即回到跨模型评审。**会话内不重试**：本
会话已确认额度耗尽的档不再重试，新会话重新从①逐档尝试。

**由来**：

- ③档由用户于 2026-08-07 批准，作为「同一个模型自己审自己会漏掉自己的盲区」这条常规
  约束的**受限例外**。
- 补偿条款的实测依据：2026-08-07 那轮 **5 视角 69 条意见打出 6 条 blocker，二轮又 8 条**，
  其中多条是主模型自述「已实测」但网格只覆盖了能通过的参数角落——所以有「不采信自述
  实测、必须自跑探针」条款。同一轮 **14 条复核掉 6 条误判**——所以有 blocker 必须独立
  复核的条款。
- **刻意不做跨会话的持久化冷却记录**（2026-08-07 两轮对抗性评审结论）：跳过即不可观测，
  一条过期或误写的记录会让③档在无人察觉的情况下变成事实默认，与「①或②任一恢复即回到
  跨模型评审」直接冲突。

## 2026-08-06 ｜ 提交与 PR 总纪律

**规则**：一律仅在用户明确要求时 commit；本地工作完成后**默认不提交**，先做本地部署/
可运行验证交付用户核验；用户明确说「提交」后落在本地 main；push 与开 PR 仍需另行明确
指令。原「达到阶段完成标准自动创建阶段提交」的行为一并收归本条——达标时报告并请求
提交指令，不再自动提交。

**要点**：授权不自动扩展——commit 授权不含 push；实施授权不含对真实数据库执行迁移或
生产环境操作。`implementer` 只写代码与迁移工具，不执行真实数据迁移。

## 其他随模板迁入的实测记录

- **2026-08-05 ｜ 代理式评审的诚实防线**（`qwen-review.md`）：首次校准运行中发生过
  「6 条测试命令全被权限系统拒绝，报告却声称『实测 215 例』并编造了失败细节」。因此
  评审提示词必须写明「被拒绝的操作必须如实标注为未执行」，且拿到输出后必须先核对

  下若被拒的是需求原文或方案文件的 Read，则**整轮作废**。
- **2026-08-12 ｜ ③档的输入边界**（`opus-review.md`）：Opus 同族评审档**暂不支持需求
  原文（`.request.md`）输入**，其评审不含独立 inventory 差集（①②两档的 plan 模式有）；
  启用③档时汇报须一并说明这一缺口。

## 2026-09-19 ｜ Codex 薄入口的确定性检查

2026-09-19 人工接力证明 Codex→Claude→次级实施→Codex 可以完成一个小任务，但每次手工
准备材料、拼接共用原则和判读结果仍会重复付成本；首次沙箱内调用曾出现 unknown 重试，授权
后的同参数调用才成功。因此新增源代码可调用的薄入口，保留完整日志、限定材料及调用上限，
不恢复冻结 A2（一个已冻结、不随公开版发布的早期原型），也不自动降级。CLI 四条纪律仍以 `CLI_DISCIPLINE.md` 为权威；参数数组从已
落盘 prompt 读取单个参数，DEVNULL、直写日志和进程监控分别落实对应语义。

2026-08-05 已发生「权限拒绝却声称实测」；新入口据结构化工具结果、拒绝字段、终结事件
判定调用有效性。`completed` 仅表示调用与必要材料读取验证通过，方案批准仍需主模型裁决。
本轮方案评审指出精选文件会遮住范围遗漏，因此补全仓路径清单和状态供指出材料缺口，
不自动外发清单外正文。两阶段 plan 物理分离材料目录，原独立清单由执行器拼入报告。
新入口及其测试加入 `CLAUDE.md` 自举清单，避免评审设施绕过自身接力。

## 2026-09-20 ｜ 薄入口大材料读取缺口

新会话将3716行路径清单列为必读，Claude分段两次超过工具25000token上限，最终仍漏读

本轮方案评审曾在读完材料后90秒思考无输出被截断；显式300秒重跑成功，默认idle据此
改300秒，总时间及日志硬界不变。该变更没有复制或放松core评审语义。


## 2026-09-21 ｜ 评审入口不等于完整接力入口

来源业务仓库的一次抽取修复已通过安装后的 Claude plan 两阶段与
最终 diff 评审；核对原始会话可见主模型直接实施，没有独立次级实施派发。前一个业务

因此新增指令型 `codex-relay`，复用评审入口、明确实施派发与主模型验收责任，以工具和

A2 状态机。独立调查请求仍按授权边界停止；不会为凑齐五环擅自实施。方案交叉评审另指出
落回覆盖并发改动、过早清理丢失产物的具体风险，入口据此要求逐文件指纹检查和有条件清理。

## 2026-09-24 ｜ 实际模型校验由精确名单改为家族匹配

2026-09-19 Fable 升到 5.1、2026-09-24 实测 `claude -p --model opus` 返回
`claude-opus-5-5`，两次都是上游同家族升级让已跑通的评审被精确名单拒绝，而当时的处置
「只追加已实证的精确值」每次升级都要再断一次、再改一次代码。用户目标是模型升级后无缝
切换，因此 `review_runner.py` 改为按别名的同家族正则全匹配（`fullmatch`，数字只认 ASCII）。

仍保留的拒绝面：跨家族（请求 opus 得到 fable/sonnet）、非数字后缀（`-extra`、`5x`、
`[1m]`）、大小写变形、全角数字、非字符串与空值；实际 ID 照旧原样写入 manifest 留证。
放弃的是「未经实证的同家族新版本一律拒」。代价：家族名本身改变（ID 不再含 `opus`/`fable`）
仍会 fail closed，留待后续开源整理的可配置化解决。

## 2026-09-24 ｜ init 插件门禁由「必须为空」改为内置插件白名单

CLI 2.1.280 在 `--safe-mode` 下 init 事件仍上报内置插件 `agents-md@builtin`、`telemetry@builtin`，
`--help` 写明安全模式下「built-in tools and plugins … work normally」，没有参数可关。执行器原要求
`plugins == []`，于是 Codex→Claude 评审在该版本上一律失败（上次通过为 2.1.258，plugins 为空）。

门禁原意是评审进程不带入外部扩展；工具集、MCP、skills、slash commands、permissionMode 与每次
tool_use 名字另有独立门禁，本次均不动。因此只放行名字、路径、来源三项都精确对上的这两个内置
插件（任意子集、不得重复），其余包括白名单外的 builtin 名一律 fail closed。用户已裁决：
`agents-md` 可能让评审方读到被审仓库的项目指令文件，可以接受。代价：CLI 以后新增或改名内置
插件仍会 fail closed，需要人工再判；版本兼容性检查留待开源整理（见 `docs/FEATURE_TODOS.md`）。


## 2026-09-24 ｜ 开源整理：个人默认值出正文、通道插件化、hook 按对象认领

**R6 必修③ 与 R8 安全一的措辞泛化**：原文「登录墙外的人」来自单一业务项目的部署形态（全部内容
在登录墙内）。公开后使用者的部署形态各不相同，照原文字面，没有登录墙的项目读不出这条判据指什么。
用户于 2026-09-24 需求核对时裁决改为「会让未授权的人拿到数据或获得访问」，R8 安全一同步泛化为
「未授权的人可达」。判据的含义（越权取得数据或访问即必修）不变，只去掉对某种部署形态的假设；
部署规模仍按项目覆写或用户配置 `defaults.deployment_scale` 传给 reviewer。

**个人默认值与模型代号移入用户配置**：2026-09-19 与 2026-09-24 两次上游模型升级都让已跑通的
评审因写死的名单或代号断掉（见上两条 2026-09-24 记录），用户目标是「模型升级、代号变化改一行
配置即可」。因此部署规模默认值、评审通道顺序、次级实施型号、插件端点与模型、实际模型家族表都
移入 `~/.config/ai-anti/config.json`。配置文件存在却无法解析时一律停下报告，不静默回落内置默认——
回落会让配置写坏之后悄悄换通道或换型号，而这正是降级阶梯「跳过即不可观测」要防的同一类失败
（2026-08-07）。

**hook 按对象认领**：开源前的交叉评审核实，安装器按整条 `SessionStart` 条目认领本工具的 hook，
条目里同时放着用户自己的 hook 对象时，重装或卸载会把用户的对象一起删掉（数据丢失，R6①）。
改为只增删 command 等于本工具命令的那一个对象，并补了混合条目的隔离测试与变异证明。
